## P2

### R3 · `needsExtendedCacheTTL` 漏判 `Extra` 注入的 1h 断点 → beta 头不发 → 上游 400

- `provider_anthropic.go:58-73`：`needsExtendedCacheTTL(req)` 只遍历**类型化请求**——`req.Messages[].Blocks[].CacheControl` 与 `req.Tools[].CacheControl`。
- 但 `buildPayload`（`:163-228`）在最后一步才 `mergeExtra(payload, req.Extra, …)`，而 `WithExtraOverrides(true)` 允许调用方把 `{"type":"ephemeral","ttl":"1h"}` 直接写进 `Extra["tools"]` / `Extra["messages"]` / `Extra["system"]`。
- **实测**：payload 上确实带了 1h 断点（`countCacheControl(payload) == 1`），而 `needsExtendedCacheTTL(req) == false` → `anthropic-beta: extended-cache-ttl-2025-04-11` 不发 → Anthropic 拒绝。
- **触发路径**：`docs/protocols.md` 明确把 `Extra` 作为"provider 特有字段"的官方逃生口，所以这不是臆想的用法。
- **为什么能存活**：`needsExtendedCacheTTL` 在仓库测试里**零引用**（`grep` 确认），beta 头的发送路径从未被验证过。
- **修复**：把判定改为对**已构建 payload** 做一次 1h 探测（复用 `countCacheControl` 的遍历形状，检出 `ttl == "1h"`），放在 `mergeExtra` 之后。这样类型化路径与 `Extra` 路径共用一条判定。

### R4 · `TestExtraReservedKeys` 依赖"DNS 必须失败"，设了代理的环境必然误报

- `audit_regression_test.go:283-290`：该用例用 `WithExtraOverrides(true)` 发一个 `http://api.test/v1` 请求，断言拿到 `*TransportError`（即假设 `api.test` 解析失败）。
- **实测失败**：`rosetta: POST http://api.test/v1/chat/completions -> 502: upstream connect failed: 不知道这样的主机。 (os error 11001)` —— 拿到的是代理返回的 `*APIError`。
- **根因确认**：进程环境里存在 `http_proxy=http://127.0.0.1:51805` / `https_proxy=…`（`os.Environ()` 实测），`httpx.New()` 的 `Transport` 为 nil → `http.DefaultTransport` → `ProxyFromEnvironment` → 请求发给本机代理 → 代理解析不了 `api.test` → 502。
- **交叉验证**：`NO_PROXY='*' no_proxy='*' go test ./...` → **全绿**。确认是环境代理，不是代码回归。
- **影响**：任何设置了 `HTTP_PROXY`/`http_proxy` 的环境（CI、企业网、容器、本机开发）都会红。这个用例实际断言的是"网络不可达"，而那是环境属性，不是被测行为。
- **修复**：给该用例注入 `WithHTTPClient(&http.Client{Transport: errTransport{}})`（一个 `RoundTrip` 恒返回 error 的 transport），把"传输失败"变成确定性构造，不再依赖 `api.test` 的 DNS 行为。
- **附带（P3，同源）**：SDK 隐式继承环境代理这一点在文档里没写。Go 对 `localhost` / 回环地址会自动跳过代理，所以本地 Ollama/vLLM 场景安全；但**内网域名**或 `http://` 端点会被送进代理（`http://` 还会让 API key 明文过代理）。`WithHTTPClient` 是唯一逃生口，`options.go:119-124` 的注释只提"proxy"两个字，没说明默认值来源与关闭方式。建议在 `docs/guide.md` 补一段。

- `partial` 的其它读路径（`Partial()` / `Err()` / `Usage()`）**全部走 `s.mu`**，唯独这里裸读。`apply()` 写 `partial` 是在锁内的（`stream.go:206-251`）。
- **当前安全性靠时序论证**：`Close()` 必须先拿到 `s.mu` 才能置 `done` 并 `releaseLocked()`，而 `apply()` 写 `partial` 在同一把锁内 —— 所以 `onEnd` 被调用时不会再有人写。`Next()` 的竞态分支（`stream.go:207-212`）也在锁内检查 `done` 后直接返回，不 apply。
- **风险**：这是一条隐式契约，没有任何注释记录。后续任何一次重构——把 `apply` 移出锁、让 `onEnd` 早于 `releaseLocked` 触发、或给 `partial` 加字段——都会变成真实 data race，而且窗口极窄，`-race` 也未必抓得到。
- **修复**：`takeOnEnd` 已经在锁内取值，把 `Model`（或整个 `partial` 快照）一并返回，回调只用快照。改动很小，把那句时序论证变成类型保证。

## P3

### R7 · 流式 `message_delta` 的 cache 字段用 `.Value != 0` 而非 `.Set`

- `provider_anthropic.go:758-776`。四个字段（`OutputTokens`/`InputTokens`/`CacheReadInputTokens`/`CacheCreationInputTokens`）的合并条件都是 `.Value != 0`。
- **实测**：`message_start` 报 `cache_read:100`，`message_delta` 显式报 `cache_read:0` → 最终仍是 `CachedInputTokens:100`。
- `FlexInt64` 的 `.Set` 字段（`B4` 引入，`internal/jsonx/jsonx.go:70-73`）本来就是为了区分"provider 没报"与"provider 报了 0"，这里没用上。
- **影响**：真实 provider 两次 usage 一般一致，罕见；但语义上"缓存完全未命中"会被误读成命中。修法：四个字段统一改 `.Set` 判定。

### R8 · `Usage.IsZero()` 不看 cache/reasoning，只报缓存的响应被记为 `UsageMissing`

- `usage.go:28-30` 只检查 `InputTokens`/`OutputTokens`/`TotalTokens`。
- **实测**：`Usage{CachedInputTokens:500, CachedCreationTokens:100}.IsZero() == true`。
- **影响**：`Stats().UsageMissing` 偏高；对只报缓存数字的 provider 会误判"无用量"而漏记账。修法：把三个 cache/reasoning 字段并入判定。

### R9 · 空 text 块的 cache 断点静默消失

- `provider_anthropic.go:285-290`：`if b.Text != ""` 才生成 wire block，空块的 `CacheControl` 随之消失。`message.go:214-233` 的 `validate()` 把空文本块当 placeholder **直接 `continue`**，既不校验也不告警。
- **实测**：`Block{Type: BlockText, Text: "", CacheControl: ExtendedCache()}` → wire 上 `countCacheControl == 0`，**无日志、无错误**。
- **场景**：调用方为了给"图片前缀"打断点而放一个空 text 占位块 → 以为整个前缀进了缓存，实际断点没上 wire，静默损失约 90% 的成本优化，且没有任何信号。
- **备注**：`countCacheControl` 的注释（`:75-78`）把这次丢弃当作既定事实并据此计数 —— **计数是自洽的**，但调用方无从得知自己的断点被吃了。
- **修复**：`validate()` 里对"空 text 块携带 `CacheControl`"报 `ErrInvalidRequest`（与"thinking 块不能带断点"同级的本地防护），或至少 `Warn`。

### R10 · 估算器不估 `Extra`；Anthropic 的输出下限没进上下文门

- `estimator.go:51-95` 的 `estimateInputTokens` 只遍历 `System`/`Messages`/`Tools`，`Extra` 注入的 payload 完全不参与估算。`Extra` 是官方逃生口，塞进大块上下文就会让门失效。
- `client.go:319-320` 用 `c.effectiveMaxOutput(req)`，它只查「请求值 → registry → 客户端默认」（`client.go:365-373`）。而 Anthropic 在 `plan()`（`provider_anthropic.go:120-142`）里对 `maxTokens <= 0` 兜底 4096，且 thinking 时还会 `b + 4096` 抬高。所以 Anthropic 下 `out` 常为 0 → `checkContext` 的 `(out > 0 && …)` 短路 → **output 侧完全不参与判定**。
- **修复**：把 Anthropic 的 4096 floor 前移到 `effectiveMaxOutput`，或让 `checkContext` 接受 `plan()` 的结果；`Extra` 侧按 JSON 序列化长度粗估。

### R11 · Anthropic 一元缺 `stop_reason` 时不校正 `tool_use`

- `provider_anthropic.go:988-992`：`r.StopReason == ""` → 直接 `StopEnd`，即使 `Content` 里已经有 `tool_call` 块。
- Responses 适配器有对应修正：`provider_openai_responses.go:864` `if out.StopReason == StopEnd && sawToolCall { out.StopReason = StopToolUse }`。Anthropic 侧没有。
- 真实 Anthropic 总会给 `stop_reason`，所以低危；但三协议对齐性有缺口，agent 循环若依赖 `StopReason` 判断"要不要执行工具"会踩空。修法：照 Responses 补一个 `sawToolCall`。

### R12 · 本机 `-race` 不可用（环境）

- `go test -race ./...` 报 `ld.exe: cannot find C:/Program: No such file or directory` —— `-race` 触发 cgo 外部链接，工具链在 `C:\Program Files\mingw64\`，**ld 无法处理路径里的空格**。
- 试过 `CC="C:/PROGRA~1/mingw64/bin/gcc.exe"`（8.3 短名）**无效**：gcc 内部仍按编译期前缀展开成 `C:/Program Files/mingw64/lib/gcc/…` 去找 `default-manifest.o`。
- **影响**：CI 在 `ubuntu-latest` 跑 `-race`（`.github/workflows/ci.yml`），门禁还在；但**本地无法复现 CI 的 race 检查**，只能靠"短路径绕过"这类手工操作（见 `docs/audit-2026-09-13-race-evidence.txt`）。
- **建议**：装一份无空格路径的 mingw-w64（如 `C:\mingw64`）并设 `CC=C:/mingw64/bin/gcc.exe`，或在 WSL / 远端 Linux 上跑本地 race 检查。这属于开发环境整理，不是代码问题。
