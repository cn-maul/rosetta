## 三、主要发现（历史发现，均已修复）

### F01 · P1 — `Partial()` 的快照复制发生在锁外，违反新增并发安全承诺

**位置**：`stream.go:180-185`；并发写入点 `stream.go:255-260`。

`Partial()` 在锁内只复制 `ChatResponse` 的浅层结构，随后解锁，再执行 `slices.Clone(cp.Content)`。此时切片仍与实时流共享底层数组。另一个 goroutine 的 `Next()` 会修改现有块的 `Text`、`Thinking` 或工具调用字段，因而快照复制与写入并发。

**触发**：一个 goroutine 消费 `Next()`，另一个 goroutine 定期读取 `Partial()`。这是 `stream.go:43-46` 明确允许的使用方式。

**验证**：定向用例并发执行 20,000 次文本增量与快照读取，race 原始输出：

```text
WARNING: DATA RACE
Write: appendBlockText()                    stream.go:260
Previous read: (*streamCore).Partial()      stream.go:184
race detected during execution of test
```

**影响**：无法保证快照一致性；发生 Go 数据竞争，不能继续宣称该路径并发安全。

**建议**：在同一个临界区内完成结构与 `Content` 克隆，再释放锁。为文本、thinking、tool-call 增量分别添加并发 `Partial()` 回归测试，并纳入 race CI。

### F02 · P2 — 流结束时持锁调用用户用量追踪器，重入流访问器会死锁

**位置**：`stream.go:199-225`、`stream.go:141-146`；外部回调链 `client.go:169-170`、`client.go:327-338`。

`Next()` 结束和 `Close()` 均持有 `s.mu` 调用 `releaseLocked()`，后者在锁内执行 `onEnd`。实际客户端的 `onEnd` 会调用用户实现的 `UsageTracker.Record`。如果追踪器同步读取所关联流的 `Partial()` / `Usage()` / `Err()`，或调用 `Close()`，就会再次申请同一个非重入锁。

**验证**：在流结束回调中启动一次 `Partial()`，它在回调返回、外层释放锁之前始终无法完成。把这次访问改为同步调用即构成自锁；附件用有界等待证明锁阻塞，不留下永久卡死测试。

**影响**：配置自定义 tracker 后，流消费或关闭可以永久阻塞。这是条件性问题，不是默认 `MemoryUsageTracker` 必然死锁。

**建议**：锁内标记释放状态并保存 model/usage/error 快照；外部回调在解锁后执行，同时保持恰好一次语义。不要通过要求用户回调“不访问流”来掩盖锁内调用外部代码的问题。

### F03 · P2 — Responses 把音频编码为不在官方输入联合中的 `input_audio`

**位置**：`provider_openai_responses.go:319-329`；相关测试 `multimodal_test.go:84-112`；文档 `docs/guide.md:84,90`。

当前 `UserAudio("listen", "QUJD", "wav")` 在 Responses 客户端上通过校验，并生成：

```json
{"type":"input_audio","input_audio":{"data":"QUJD","format":"wav"}}
```

本次读取的 OpenAI 官方 SDK `ResponseInputContentParam` 仅包括 text、image、file，没有该音频输入类型。实现把 Chat Completions 的形状直接当作 Responses 的标准能力，现有 map 断言测试也锁定了同一个错误形状。

**影响**：按照当前指南对官方 Responses 使用音频会构造不符合官方契约的请求，不能据此保证调用成功。第三方网关支持某个私有扩展不等于官方支持。

**建议**：官方 Responses 路径对该组合本地返回 `ErrInvalidRequest` 或明确的能力错误；音频路由到支持该输入的 Chat Completions 模型。若需支持第三方扩展，应显式启用，不默认冒充标准协议。同步修改测试和能力矩阵。

**官方依据**：见文末 S1。

### F04 · P2 — Rerank 对 Voyage、DashScope 的兼容承诺与实现不符

**位置**：`rerank.go:10-13,89-107,123-149`、`aux.go:56`；声明 `docs/guide.md:198`、`CHANGELOG.md:10`。

当前统一发送平铺 JSON 到 `/rerank`，使用 `top_n`，只解析顶层 `results[]` 和 `document.text`。这不是列出的所有服务商的共同协议。

**Voyage**：官方请求参数是 `top_k`，响应是 `data[]`，回带 `document` 为字符串。回放官方形状：

```json
{"data":[{"index":0,"relevance_score":0.9,"document":"doc"}]}
```

实际结果：

```text
payload top_n=1 top_k=<nil>
rosetta: rerank response contains no results
```

**DashScope**：官方文档列出 `qwen3-rerank` 使用 `/compatible-api/v1/reranks`（复数）；其他如 `gte-rerank-v2` 原生路径为 `/api/v1/services/rerank/text-rerank/text-rerank`，负载使用 `input` / `parameters`，响应为 `output.results`。只调整本库基地址无法同时解决固定后缀和负载/响应嵌套。

本地回放观察：

```text
path=/api/v1/services/rerank/text-rerank/rerank
query=q input=<nil> parameters=<nil>
rosetta: rerank response contains no results
```

**影响**：用户按文档配置这些服务会遇到错误路径、参数或成功响应无法解析；`Extra` 不能弥补固定响应解析问题。

**建议**：短期把兼容范围缩到经过契约验证的 Cohere-compatible 接口；长期按供应商/协议增加适配层，包括路径、TopN 参数名、响应容器、文档字段与 usage。不要用一份 Cohere 模拟响应验证所有供应商。

**官方依据**：S5、S6。上述为官方契约对照和本地回放，未调用真实远端。

### F05 · P2 — 缺失及 `null` 数值字段被解码为零，异常结果被当作成功

**位置**：`embedding.go:114-117,136-147`；`rerank.go:123-129,153-164`。

直接将 index/score 解码到 `int` / `float64`、向量元素解码到 `float32`，无法区分合法的零与缺失/`null`。后续范围和有限值校验拦不住这些情况。

**最小复现及实际结果**：

```go
decodeEmbeddingsResponse([]byte(`{"data":[{"index":null,"embedding":[null,0.5]}]}`), 1)
// err=nil, Index=0, Embedding=[0, 0.5]

decodeRerankResponse([]byte(`{"results":[null]}`), 2)
// err=nil, Results=[{Index:0, RelevanceScore:0}]

// results:[{}] 同样被当作成功。
```

**影响**：服务端/网关返回结构错误时，调用方可能把文档 0 误认为有效结果，或将伪造的零向量元素写入索引。不是所有数值 0 都有问题；问题是字段是否存在且为数字没有被验证。

**建议**：wire 层对必需字段使用指针或自定义解码，拒绝 null/缺失 result、index、score 与 null 向量元素，再执行现有范围、唯一性及数值检查。

### F06 · P2 — Embedding 不检查显式请求维度，也不检查批内维度一致性

**位置**：`embedding.go:98`、`embedding.go:144-147`。

解码函数只获得输入数量，没有获得 `Dimensions`，检查向量时只判断非空。

**验证**：请求 `Dimensions:2`，两个输入；回放向量分别为 `[1]` 和 `[1,2,3]`。结果成功返回：

```text
requested dimensions=2, returned dimensions=1,3
err=nil
```

现有 `embedding_test.go:22,27-29,37` 也存在请求 256 维、用两维模拟返回验证成功的测试样例，未覆盖此契约。

**影响**：错误维度直到向量库入库或相似度计算时才暴露，可能造成部分批次入库失败或下游计算错误。不能让响应数量校验给调用方造成“向量结构完整”的误解。

**建议**：显式 `Dimensions>0` 时要求每个向量严格匹配；未指定时至少要求同批维度一致。只报告协议错误，不自行截断或补零修复上游向量。

### F07 · P2 — 未校验角色与块类型组合，文件/音频可能静默消失

**位置**：`message.go:182-196`；`provider_openai_chat.go:141-175`；`provider_openai_responses.go:247-276`；`provider_anthropic.go:181-184`。

公共校验只验证角色是否合法、每个块字段是否完整，没有验证角色是否允许该块。system 分支只抽取文本；OpenAI assistant 分支也只处理部分块。

**复现**：system 消息包含以下块，再跟一条正常 user 消息：

```go
[]Block{
    {Type: BlockText, Text: "read attached"},
    FileRef("secret.pdf", "file-secret"),
    AudioContent("QUJD", "wav"),
}
```

三个协议均可以成功构建，但只留下 system 文本，文件和音频消失。Anthropic 因为先走 system 文本提取，连通常应触发的“不支持音频”错误也被绕过。另 `AssistantBlocks(FileRef(...))` 在 Chat 中变成空 assistant 文本，在 Responses 中直接消失。

**影响**：请求表面成功，模型实际没有看见用户要求的资料，答案可能产生误导。此处不要求所有角色都支持媒体；**不支持应明确拒绝，不能悄悄删除。**

**建议**：建立按协议划分的 role × block 支持矩阵；编码器对无法表达的非空块返回 `ErrInvalidRequest`。测试必须从公开 `Chat/ChatStream` 入口覆盖组合，而不只是单独调用编码函数。

### F08 · P2 — Anthropic 普通文本文件被错误地编码为 base64 PDF source

**位置**：`provider_anthropic.go:295-303`。

内联文件不论 MIME 类型都生成 `source.type="base64"`。官方 Anthropic base64 document source 限 `application/pdf`；`text/plain` 应使用 `type="text"`，其 data 是解码后的文本。

**复现**：

```go
UserFile("read", "a.txt", "text/plain", "SGVsbG8=")
```

当前生成：

```json
{"type":"document","source":{"type":"base64","media_type":"text/plain","data":"SGVsbG8="},"title":"a.txt"}
```

**影响**：合法的文本文件输入被编码成不符合官方契约的对象；当前任意 MIME 透传会把错误延迟到上游。

**建议**：按 MIME 分支实现：PDF 使用 base64；纯文本将调用方约定的 base64 解码成文字后生成 text source；未支持的 MIME 本地报错。不要把所有文件自动伪装成 PDF。

**官方依据**：S3、S4。

### F09 · P2 — 嵌入新增 `user` 保留键意外阻断 Chat 的合法扩展字段

**位置**：`request.go:117,127-130`；`provider_openai_chat.go:128-129`。

`reservedPayloadKeys` 是全局集合。为 Embedding 增加 `user` 后，Chat 的 `Extra["user"]` 也被拒绝；但 `ChatRequest` 没有对应 `User` 字段，并不存在调用方覆盖 SDK 管理字段的问题。

**复现**：

```go
&ChatRequest{
    Model: "m", Messages: []Message{User("x")},
    Extra: map[string]any{"user": "end-user-id"},
}
```

返回：

```text
rosetta: invalid request: Extra key "user" collides with an SDK-managed field
```

**影响**：原本通过 Extra 传递终端用户标识的 Chat 调用失败；用户不得不全局开启 `WithExtraOverrides(true)`，连带关闭其他有价值的字段保护。

**建议**：按操作/协议定义保留键，而不是维护所有 API 字段的并集。增加 Chat 的 `Extra.user`、Embedding 的 `Extra.user` 分别应允许/拒绝的测试。

### F10 · P2 — 大于 4 KiB 的错误 JSON 先截断再脱敏，敏感键保护失效

**位置**：`errors.go:109-119,128-132,144-154`。

`safeTruncateBody` 先调用 `truncateBody`。当原始 JSON 超过 4 KiB 时，该函数已经把截断片段转为 JSON 字符串；后续 `redactJSON` 只能看到字符串，无法遍历其中的 `api_key`、`authorization`、`password` 等字段。最终只剩 `sk-...` 模式替换，非该格式的凭据会保留。

**验证**：

```go
body := []byte(`{"api_key":"provider-secret-123456","padding":"` +
    strings.Repeat("x", 5000) + `"}`)
raw := safeTruncateBody(body)
// raw 仍包含 provider-secret-123456。
```

**影响**：错误体大小改变了敏感键脱敏是否生效，错误日志/遥测可能保存供应商回显的非 `sk-` 凭据。指南已提醒错误可能含内容，但本次明确宣称的敏感键脱敏在该边界下没有执行。

**建议**：在现有有界响应体内先解析并脱敏、再截断；对无法解析的内容采取保守策略。增加 4 KiB 边界、嵌套字段、非 `sk-` token、JSON/非 JSON 场景测试。该修复也不意味着可以把完整 `APIError.Message` 当作安全日志。

### F11 · P2 — Responses 将 reasoning 的“值不支持”误当作“字段不支持”，且跨模型永久降级

**位置**：`provider_openai_responses.go:72-76`；后续 sticky 应用 `:45-46`；字段发送 `:188-192`。

`sanitize` 通过关键词决定删除 reasoning。服务端只拒绝某模型的某个 effort 值时，也会触发整字段删除和客户端级记忆。

**本地 HTTP 复现**：同客户端先请求模型 A 的 `EffortLow`，服务端返回：

```json
{"error":{"type":"invalid_request_error","code":"unsupported_value","param":"reasoning.effort","message":"Unsupported value: 'reasoning.effort' does not support 'low' with this model. Supported values are: 'high'."}}
```

然后请求模型 B 的 `EffortHigh`，其本来支持此参数。观察：

```text
request[0]: model=gpt-5-pro reasoning=map[effort:low]
request[1]: model=gpt-5-pro reasoning=<nil>
request[2]: model=gpt-5 reasoning=<nil>
firstErr=<nil> secondErr=<nil>
```

模型名只是本地模拟场景标识，不是本次对官方模型服务进行实测。

**影响**：第一次错误被掩盖；后续其他模型显式要求的推理强度也无声丢失，质量、费用与延迟可能偏离预期。

**建议**：区分 `unsupported_value` 与未知字段；值错误保留原错误，不删除整个字段。能力缓存至少按模型/字段隔离，只有明确的端点级拒绝才使用全局 sticky。

### F12 · P2 — 真实 HTTP 中断常返回 `unexpected EOF`，绕过截断哨兵且丢失已知 usage

**位置**：`provider_openai_chat.go:446-453`、`provider_openai_responses.go:386-393`、`provider_anthropic.go:462-469`。

新增截断分支只识别 `io.EOF`。真实 chunked HTTP 连接在终止零块之前断开时，Go 返回 `io.ErrUnexpectedEOF`，三协议会直接返回该错误，不合成携带已知 usage 的结束事件。

**复现方法**：`httptest` 使用 `http.Hijacker` 写入合法 SSE chunk，随后关闭连接，不写 `0\r\n\r\n`，也不发送 provider 终止事件。核心：

```go
fmt.Fprintf(rw,
    "HTTP/1.1 200 OK\r\nContent-Type: text/event-stream\r\n"+
        "Transfer-Encoding: chunked\r\n\r\n%x\r\n%s\r\n",
    len(body), body)
rw.Flush()
conn.Close()
```

三个协议实际均为：

```text
err=unexpected EOF
errors.Is(err, io.ErrUnexpectedEOF)=true
errors.Is(err, ErrStreamTruncated)=false
MessageEnd count=0
Partial.Text()="partial"
```

Chat 已收到的 `prompt_tokens=5, completion_tokens=2`、Anthropic 已收到的 `input_tokens=5, output_tokens=1` 没有被交付，最终 `Usage()` 为零。Responses 复现没有预先收到 usage，因此不把其零值单独算作丢失证据。

**影响**：错误并未被当作成功，但调用方匹配 `ErrStreamTruncated` 的恢复分支失效，且用量统计遗漏。

**建议**：至少纳入 `io.ErrUnexpectedEOF`；先交付已知 usage，再返回既可匹配截断哨兵、又保留底层原因的错误。取消/超时保持可区分。增加真实 HTTP 断开测试，不只测试 `strings.Reader` 的普通 EOF。

### F13 · P2 — 对每个空文本块一律报错，破坏已有“空文本占位 + 有效媒体”输入

**位置**：`message.go:202-205`、`request.go:180-184`；原编码器例如 `provider_openai_chat.go:217-225`。

**准确触发条件**：调用方手工组合 `Message.Blocks`，其中有空文本占位和有效图片。不是所有纯图片请求都失败；`UserImage("", url)` 本身会省略空文本块，仍正常。

```go
Message{Role: RoleUser, Blocks: []Block{
    {Type: BlockText, Text: ""},
    {Type: BlockImage, ImageURL: "https://example.com/a.png"},
}}
```

旧版本未逐块拒绝，编码器会跳过空文本生成有效纯图片请求。当前直接构建 payload 仍能正确生成，但公开 `Chat/ChatStream` 在公共校验阶段均返回：

```text
Messages[0]: Blocks[0] (text): text block is empty
```

**影响**：动态组装文本/图片内容的已有调用方式回归，即使消息总体存在有效内容也被拒绝。

**建议**：在规范化阶段忽略空文本块，再检查整条消息是否还有可表达的有效内容；不要为了拒绝完全空消息而同时拒绝合法媒体消息中的空占位。补公开入口测试。

## 四、补充边界与能力限制（历史发现，均已处理）

以下不计入前述 13 项主要发现；已观察到的行为与未证明的风险分开列出。

1. **Responses URL 文件是被错误解释为协议限制的功能缺口。** `provider_openai_common.go:20-27` 和 `provider_openai_responses.go:330-343` 拒绝 http(s) 文件 URL；但官方 `ResponseInputFileParam` 有 `file_url`（S2）。这是当前已文档化拒绝的子集限制，不等于已有受支持调用被破坏。建议 Responses 单独映射 `input_file.file_url`，至少更正文档“不支持”的协议归因，Chat 的规则不要共用。
2. **文件双来源存在歧义。** `message.go:217-220` 只检查 FileData/FileID 至少一个非空，不拒绝两者同时非空。三个协议都优先旧 FileID，例如 `FileData:"TkVX", FileID:"file-old"` 会丢弃新内容。建议 XOR 校验，或明确且一致地文档化优先级；不要让调用者误以为更新 FileData 就替换了已上传文件。
3. **媒体内容校验仅为外层非空。** 空 data URL `data:application/pdf;base64,` 和 `not-base64!` 音频仍可通过相关构建路径。建议基础 data URL/base64 语法及非空载荷校验；不要求 SDK 验证真实音频编码或完整 PDF。
4. **`WithExtraOverrides(true)` 后的响应校验仍按覆盖前请求数量。** `embedding.go:91-98`、`rerank.go:100-107` 在 Extra 覆盖 input/documents 后，用原切片长度验证响应。该选项已明确“覆盖风险自负”，故不作为主要漏洞；但可以派生最终有效请求再校验，或限制不能正确支持的覆盖项。
5. **辅助响应的排序与 token 数没有全面规范化。** `embedding.go:147`、`rerank.go:168` 按服务端顺序返回；负 usage 也可以进入 tracker。对严格遵守协议的上游未必出错，需明确 API 是保证“返回已排序结果”，还是信任服务端；建议测试乱序 index、乱序 score、TopN 超量和负 usage，拒绝异常统计而非静默计入。
6. **`DisableThinking` 在不发生合并时不规范化。** `registry.go:138` 的单层直接赋值不会执行 `mergeInfo` 中撤销逻辑。已复现仅手动条目同时设 `SupportsThinking:true, DisableThinking:true` 时，Lookup 仍返回支持 thinking。属于矛盾输入边界；建议安装每条模型记录时统一应用显式撤销，而不依赖是否存在第二层同 ID。
7. **非法端点构建错误仍回显原 URL。** `client.go:52-57` 拒绝 query 后，在错误中用 `%q` 输出完整端点；若用户误将密钥放 query，构建错误仍包含该凭据。主/辅助端点错误均建议仅记录脱敏 URL。这不意味着发送了该 URL：校验确实阻止了网络调用。

其他能力说明：

- 视频块、帧和时间戳当前未建模；`BlockType("video")` 会报 unknown block。用户所说“多模态”不能自动理解为已支持视频，这属于能力范围，不作为新增回归。
- 空 `WithEmbeddingAPIKey("")` 继续继承主 key 是当前已文档化行为，不列为确认漏洞。将辅助端点指向另一服务时，调用者应显式配置该服务的凭据，避免无意复用。
- Anthropic `FileRef` 是否需要特定 beta 头未获得足够确定证据，本报告不把它认定为必现缺陷。
- 图片普通 user URL/data URL 路径未发现本轮新增转换破坏；不等于对所有图像格式、分辨率、模型进行了远端认证。
